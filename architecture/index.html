    Architecture¶

    This document describes the runtime architecture, the ingestion and retrieval paths, tenant isolation, and the reliability model. The longer design baseline is in DESIGN.md.

    Goals¶

    • Turn digital documents into versioned, authorization-scoped evidence.
    • Answer questions only from evidence the caller is allowed to read, with citations.
    • Keep ingestion asynchronous and operable: retries, idempotency, dead letters, and reconciliation.
    • Run as a modular monolith with a separately deployable parser and worker.
    • Make tenant isolation explicit in the application and optionally enforce it in PostgreSQL.

    Non-goals¶

    • OCR, image understanding, or arbitrary agent code execution.
    • A plugin for every storage or model vendor.
    • Kubernetes/Helm delivery in the current release.
    • Treating Wiki or graph projections as required for basic evidence RAG.

    Ingestion path¶

    sequenceDiagram
    participant U as User
    participant A as API
    participant DB as PostgreSQL
    participant O as Outbox
    participant Q as Redis/Asynq
    participant W as Worker
    participant D as docreader

    U->>A: POST /knowledge-bases/:id/documents
    A->>A: authorize + validate format/size
    A->>D: store original object
    A->>DB: document + version + pipeline RUNNING
    A->>O: pipeline event (same transaction)
    O->>Q: publish task
    Q->>W: parse → normalize → chunk → embed → index
    W->>D: parse original
    W->>DB: stages, chunks, embeddings, evidence package
    W->>DB: version EVIDENCE_READY
    W->>O: completion event
    U->>A: poll document status
    A-->>U: pipeline status + stages

    Key properties:

    • The upload response is a pipeline handle, not a promise that parsing finished. Clients poll the document status or watch the document list.
    • The outbox row is written in the same transaction as the state change. A crash after commit still results in publication.
    • Tasks are idempotent: re-delivery does not create duplicate chunks or evidence.
    • Only the current version in EVIDENCE_READY is searchable. Replacing a document retires the previous version from retrieval.
    • A failed stage records a stable error code and can be retried from operations endpoints or the UI.

    Retrieval and answer path¶

    sequenceDiagram
    participant C as Client
    participant A as API
    participant DB as PostgreSQL
    participant M as Model
    participant S as SSE

    C->>A: POST /search or POST /sessions/:id/messages
    A->>A: authenticate + authorize KB
    A->>DB: BM25 recall (tenant/KB/current version/EVIDENCE_READY)
    A->>DB: vector recall (same scope)
    A->>A: RRF fusion + dedupe
    A->>A: optional rerank
    A->>DB: parent/neighbor expansion + final authorization
    A->>M: prompt with evidence only
    M-->>A: answer + citation IDs
    A->>A: validate citations against this run's evidence
    A->>S: status/references/answer/complete
    A->>DB: persist message, citations, events
    S-->>C: streamed events
    • BM25 and vector recall run in parallel and are merged with reciprocal rank fusion.
    • Every query carries tenant, knowledge-base, current-version, and EVIDENCE_READY predicates. A second authorization pass runs before delivery.
    • Citations are first-class data. The model can only cite registered evidence IDs; unresolvable or unauthorized citations are rejected.
    • Insufficient evidence produces a refusal with insufficient_evidence, not a general-knowledge answer.
    • Async answers persist events before streaming them. Clients can resume from after/Last-Event-ID; a worker restart produces a terminal event instead of a stream that never ends.

    Tenant isolation¶

    flowchart LR
    P[Principal<br/>session or API key] --> S[Authorization scope]
    S --> T[Tenant]
    T --> K[Knowledge base membership]
    K --> Q[Scoped SQL]
    Q --> R[(PostgreSQL)]
    R -. optional .-> L[Row-level security]

    Defense in depth:

    1. Authentication establishes a principal and tenant.
    2. Every knowledge-base operation resolves membership and action.
    3. SQL queries inject tenant_id and knowledge-base scope; static checks reject new unscoped GORM paths.
    4. Retrieval re-checks that chunks belong to the current version and the caller's authorized evidence set.
    5. TENANT_RLS_MODE=enforce adds PostgreSQL row-level security with separate runtime roles for defense in depth. Production startup rejects shadow/off when APP_ENV=production.

    Reliability primitives¶

    Primitive Purpose
    Outbox Publish tasks/events in the same transaction as state changes
    Inbox/lease Deduplicate and serialize task claims across workers
    Idempotency key Prevent duplicate uploads and repeated answer generation
    Stage state machine Track parse/normalize/chunk/embed/index progress and failures
    Dead letters Preserve failed tasks for inspection and replay
    Reconcile Repair expired leases and interrupted pipelines
    Retention/cleanup Purge soft-deleted documents and expired task history

    Wiki and relation projections are optional. They reuse the evidence pipeline and authorization ports, run on a separate queue, and never block evidence RAG when they fail. See DESIGN.md for the projection join semantics.

    Deployment¶

    The supported deployment is Docker Compose:

    • deploy/docker-compose/docker-compose.yml: local development stack.
    • deploy/docker-compose/quickstart.compose.yml: local-only overlay with development identity and deterministic models.
    • deploy/docker-compose/release.compose.yml: pinned release images for api and docreader; the web UI is a static bundle.

    Release images are scanned, published with CycloneDX SBOMs, and signed with cosign. Upgrade order is migrate → docreader → worker → api. See Releases and Operations.

    Capability boundaries¶

    • Digital PDFs only; no OCR for scanned or mixed PDFs.
    • One embedding model/dimension per knowledge base; changing it requires a managed re-index.
    • Rerank is opt-in and off by default.
    • Only the http_manifest connector is implemented.
    • Kafka, OpenSearch, Neo4j, and Kubernetes are not part of the current runtime.

    These boundaries are intentional: the platform prefers a small, testable core over feature-count parity.
