# B22 PRD 草稿：MCP 连接可运营化

- 状态：草稿，待 owner 评审；未纳入 MILESTONES，不改变 A 段与企业 GA 门禁
- 日期：2026-11-12
- 关联：B16（MCP Server + SDK，已完成）、B21（MCP 配置页，已完成）、B17（对外评测）、B18（证据链审计）
- 范围边界：本文只讨论 MCP 接入体验、工具契约与分发；HTTP/SSE 远程传输和写操作工具列为 P2，需单独立项

## 1. 背景与问题

B16 交付了 stdio MCP Server 与 8 个工具（7 个只读 + `ask`），B21 交付了工作台接入页：选择单个知识库 → 生成仅含 `knowledge_base:read` + `chat` 的 scoped Key → 复制 `mcpServers` 配置。真实客户端已验证 `list_knowledge_bases → list_documents → search → ask → get_citation` 与越权负向。

当前问题不是“能不能接”，而是“接上之后是否可运营”：

1. **单库限制是页面策略，不是能力边界**。后端 Key 支持多个 `knowledgeBaseIds`，但页面只允许一个；需要跨库的团队只能写 curl 或生成多个 Key。
2. **配置完不知道通没通**。页面生成后没有连通性自检，失败原因（Key 错、网络、模型不可用、文档未就绪）要用户自己排查。
3. **缺少客户端差异**。只给通用 JSON，Qoder、Claude Desktop、Cursor 的配置文件位置和重启方式不同。
4. **分发门槛高**。Release 没有 `rag-mcp` 二进制，用户必须装 Go 或 Docker 自行编译。
5. **用量不可见**。`/ops` 只显示 Key 的 `lastUsedAt`，看不到哪个工具被调用、成功率、失败原因。
6. **工具面向 LLM 的可用性不足**。缺少 MCP Resources/Prompts，客户端只能靠工具描述猜测“先搜再问”；长文档和宽检索容易撑爆上下文。

## 2. 定位与目标

**定位**：把 MCP 从“一个能连的 Server”升级为“可创建、可自检、可观察、可分发”的受权知识连接。

**成功标准**（上线后 30 天）：
- 从生成 Key 到首次成功工具链的中位耗时 ≤ 5 分钟；
- 生成 Key 后 24h 内完成一次成功调用的激活率 ≥ 60%；
- 连接相关支持问题中，“配置错误/密钥错误”占比下降 50%；
- 越权负向零泄漏；MCP 相关工具调用成功率 ≥ 99%（排除模型超时）。

**非目标**：
- 不新建第二套权限体系，MCP 一律复用 API Key + `AuthorizationScope`；
- 不做通用数据导出、任意 SQL/图查询代理；
- 不在本 PRD 内默认开放写操作；
- 不托管用户数据副本，MCP Server 仍是无状态转发。

## 3. 用户与任务

| 用户 | 任务（JTBD） | 当前阻塞 |
| --- | --- | --- |
| 桌面 AI 助手用户（Qoder / Claude Desktop / Cursor） | 让助手基于公司知识库回答，并能点回原文 | 配置繁琐、不知道是否连通、只能单库 |
| 平台/Agent 开发者 | 在 Dify、n8n、自研 Agent 中把知识库当工具 | stdio 不便远程部署；无用量与失败信号 |

| 安全/合规 | 证明“回答只来自授权证据” | 工具级调用不可追溯（当前只有 HTTP 指标） |

## 4. 现状与差距

| 能力 | 现状（B16/B21） | 差距 |
| --- | --- | --- |
| 鉴权 | 复用 `rk_` API Key；能力集与 KB 范围收窄创建者权限；撤销立即生效 | 无按 Key 的调用统计与工具级审计 |
| 知识库范围 | 后端支持多库；页面固定单库 | 页面不能多选；无“连接”视图 |
| 工具 | 8 个：list/get/search/ask/citation/status | 缺省 KB 需每次传；无资源与提示词 |
| 上下文控制 | `search` 仅透传 `sessionOverride` 字符串 | 无直观的 topK/上下文预算参数 |
| 自检 | 页面给出步骤，需用户手工验证 | 无“一键测试连接” |
| 客户端配置 | 通用 `mcpServers` JSON | 无 Qoder/Claude/Cursor 模板与路径提示 |
| 分发 | 源码 `go build` / Docker 交叉编译 | Release 无二进制、无签名资产 |
| 用量 | Key `lastUsedAt` + HTTP 指标 | 无工具级成功/失败/延迟视图 |

## 5. 方案总览

按优先级拆三段，B22-A 为 MVP，B22-B 为增强，B22-C 单独立项：

- **B22-A 连接可用（P0）**：多库连接、连接自检、客户端模板、发布二进制、Key 过期预设。
- **B22-B 连接好用（P1）**：MCP Resources/Prompts、默认知识库、工具级用量与审计、按 Key 限流、npx/uvx 包装。
- **B22-C 连接扩展（P2，需单独批准）**：HTTP/SSE 远程传输、写操作工具、跨库联邦检索。

## 6. 功能需求

### B22-A（P0）

#### FR-1 多知识库连接

**用户故事**：作为需要同时查询多个库的开发者，我可以在接入页选择 1 个或多个知识库，生成一个 Key，并在配置中看到它的作用范围。

- 接入页知识库选择改为多选，默认仍为单库；选择 >1 时提示“范围越大，泄露面越大”，并要求确认。
- 请求仍复用 `POST /api-keys`：`capabilities` 固定为 `["knowledge_base:read","chat"]`，`knowledgeBaseIds` 为所选集合；不提供“全租户”选项。
- 配置卡片展示 Key 的作用域列表；`/ops` Key 列表展示同样的知识库范围。
- MCP 工具调用仍要求显式 `knowledgeBaseId`；服务端按 Key 范围校验，越权返回 403。
- 兼容：已生成的单库 Key 不需要迁移。

**验收**：
- 选择 2 个库生成 Key，分别对两个库 `search`/`ask` 成功；对第三个库调用返回 403；
- Key 能力集恰为 `knowledge_base:read` + `chat`；
- 非 `tenant:admin` 不可创建；跨租户知识库不可见、不可提交；
- 前端使用生成类型，OpenAPI 无漂移。

#### FR-2 连接自检

**用户故事**：作为刚生成 Key 的用户，我可以在页面点击“测试连接”，看到每一步是否通过以及失败原因。

- 生成 Key 后（token 仍在内存中）展示“测试连接”按钮，依次执行：
  1. `GET /knowledge-bases`：Key 有效、租户可解析；
  2. `GET /knowledge-bases/{id}/documents?limit=1`：所选库可读；
  3. `POST /search`（固定查询，如 `hybrid recall`）：检索通道可用；
  4. 可选 `POST /sessions` + 一次 `ask`：模型可用（可能较慢，默认不勾选）。
- 每步显示状态、HTTP 状态码、耗时与可操作建议（401 = Key 无效/已撤销；403 = 范围不含该库；409 = 文档未就绪；超时 = 网络或模型不可用）。
- 自检只使用当前会话内存中的 token；页面不落盘、不写日志、不回显已保存 Key。
- 对已保存的连接，允许用户粘贴 Key 做一次自检（password 输入，不持久化）。

**验收**：
- 正确 Key 全部通过；撤销后的 Key 第一步 401；去掉库范围的 Key 第二步 403；错误 API 地址显示网络错误；
- 自检不会产生额外文档或改变知识库状态；
- 刷新页面后无 Key 明文残留。

#### FR-3 客户端配置模板

**用户故事**：作为桌面客户端用户，我可以直接复制适配我客户端的配置，不需要查文档。

- 提供 Qoder、Claude Desktop、Cursor 三个 tab，内容为对应 `mcpServers` JSON；通用模板保留。
- 展示各客户端配置文件路径与重启提示（macOS/Windows 分开），并注明远程/容器部署时 `RAG_API_URL` 要改成客户端可达地址。
- 支持一键复制；API 地址与二进制路径可编辑，配置实时生成。

**验收**：
- 三个模板均能被对应客户端加载（至少 Qoder 与 Claude Desktop 实测）；
- 模板中的 Key 只在生成后的当前会话出现，刷新后为占位符。

#### FR-4 发布与分发

**用户故事**：作为没有 Go 环境的用户，我可以从 Release 下载与系统匹配的 `rag-mcp` 二进制并校验。

- Release workflow 增加 `rag-mcp` 构建矩阵：linux/darwin/windows × amd64/arm64；产物进入 `SHA256SUMS` 并用现有 cosign keyless 流程签名 `SHA256SUMS`。
- 提供 `ghcr.io/.../rag-mcp` 镜像（stdio 用法：`docker run -i --rm -e RAG_API_URL -e RAG_API_KEY ...`）。
- 接入页“二进制获取”区域链接最新 Release，并显示当前页面版本对应的 MCP Server 版本。
- 兼容性说明：MCP Server 版本、API 版本、工具 schema 版本三者对应关系写入 `docs/mcp.md`。

**验收**：
- 至少 linux/amd64、darwin/arm64、windows/amd64 三个产物在干净环境可运行并通过 `initialize` + `tools/list`；
- `sha256sum -c` 与 `cosign verify-blob` 通过；
- 页面链接与 Release 资产一致。

#### FR-5 Key 过期预设

**用户故事**：作为管理员，我希望 MCP Key 默认有有效期，降低长期凭据风险。

- 接入页提供 7/30/90 天与“不过期”选项，默认 30 天；写入 `expiresAt`。
- 过期时间在页面、`/ops` 列表和客户端配置说明中可见。

**验收**：创建后 `expiresAt` 正确；过期 Key 调用返回 401；页面展示剩余天数。

### B22-B（P1）

#### FR-6 MCP Resources

**用户故事**：作为支持 Resources 的客户端用户，我可以把文档当资源浏览和读取，而不是先调工具。

- 提供资源模板：
  - `rag://knowledge-bases/{kbId}`：知识库摘要与文档计数；
  - `rag://knowledge-bases/{kbId}/documents/{docId}`：文档元数据、当前版本、处理状态；
  - `rag://documents/{docId}/content`：解析内容块（仅 `EVIDENCE_READY`）。
- 每次资源读取都重新执行服务端授权；越权返回 MCP 错误，不返回空内容伪装成功。
- `resources/list` 只返回 Key 范围内的知识库根，文档级通过模板按需读取，避免一次枚举大量文档。

**验收**：客户端可 `resources/list` + `resources/read`；越权资源失败；内容与当前版本一致；删除/替换版本后旧资源不可读。

#### FR-7 MCP Prompts

**用户故事**：作为客户端用户，我可以使用标准提示词，让回答稳定地带引用。

- 提供 `grounded_answer`：参数 `knowledgeBaseId`、`question`；提示模型先检索、只基于证据回答、无证据时拒答、引用必须来自证据。
- 提供 `evidence_review`：参数 `question`、`answer`、`citations`；用于检查引用是否支撑结论。
- Prompt 只返回消息内容，不代客户端调用工具；模板纳入 `config/prompt_templates/` 管理，不在 Go 代码写 Prompt 字面量。

**验收**：`prompts/list` 可见；`prompts/get` 返回渲染后的消息；模板变更启动时校验；不影响现有 `ask`。

#### FR-8 默认知识库与参数简化

- 新增可选 `RAG_DEFAULT_KNOWLEDGE_BASE_ID`：当 Key 只绑定一个库时，工具可省略 `knowledgeBaseId`。
- `search` 增加可选 `topK`（1–50）与 `contextTokenLimit`（500–8000），由服务端既有校验与三级覆盖执行；非法值返回工具错误。
- 保持向后兼容：旧参数与旧客户端行为不变。

**验收**：单库连接可省略 `knowledgeBaseId`；多库连接省略时返回明确错误；越界参数报错；检索结果与 Web 端同配置一致。

#### FR-9 用量与工具级审计

**用户故事**：作为管理员，我可以看到每个 MCP 连接的调用量、成功率、最近错误。

- MCP Server 在请求中附带 `X-MCP-Tool` 与 `X-MCP-Client`（客户端名/版本，可空）。
- API 在存在 `X-MCP-Tool` 时写入工具调用审计（Key ID、租户、工具、状态码、耗时）；该头仅用于统计，**不参与授权**，可被伪造，安全决策仍只依赖 Key。
- `/ops` 增加“MCP 连接”视图：按 Key 聚合调用数、成功率、P95 延迟、最近错误与最近使用时间；数据保留期与审计一致。
- 提供指标与告警阈值：工具错误率、401/403 比例、超时率。

**验收**：调用后 `/ops` 可见聚合；撤销 Key 后停止计数；伪造 `X-MCP-Tool` 不改变授权结果；审计查询跨租户为零。

#### FR-10 按连接限流与分发增强

- 在现有租户配额/限流之上增加按 Key 的可选速率限制（例如 60 次/分钟），超限返回 429 与 `Retry-After`。
- 提供 `npx @rag-platform/mcp` 与 `uvx rag-platform-mcp` 包装（下载对应平台二进制），降低安装门槛；包装器不处理凭据持久化。

**验收**：限流生效且不影响其他 Key；包装器在干净 Node/Python 环境启动并完成 `tools/list`。

### B22-C（P2，单独立项）

- **HTTP/SSE 远程传输**：服务端托管 MCP 会话，OIDC/API Key 鉴权，按租户隔离；需重新评估会话、超时、审计与 DoS 面。
- **写操作工具**：上传、移动、打标签、权限变更；必须二次确认、独立能力位、审计与最小权限，默认关闭。
- **跨库联邦检索**：一次调用检索 Key 范围内多个库并融合；需定义跨库去重、引用与权限边界。

以上三项在客户需求或设计伙伴确认前不进入 B22-A/B 的实现范围。

## 7. 契约与兼容

- 工具新增参数一律可选，不改现有字段语义；`tools/list` 中的 JSON Schema 同步更新。
- 新工具/资源/提示词遵循 MCP 规范，不引入自定义传输。
- `rag-mcp` 版本与 API 版本解耦：至少保证 N 与 N-1 工具 schema 兼容；不兼容变更需要新工具名或版本化。
- OpenAPI 不变（B22-A 只改前端与发布）；若 FR-9 增加审计查询接口，则同步 OpenAPI、生成类型与契约测试。
- SDK（TypeScript/Python）不因 B22 破坏现有方法；新增能力按需追加。

## 8. 权限、安全与审计要求

- 单一权限来源：API Key + `AuthorizationScope`；MCP 不新增 ACL，不新增旁路。
- Key 只能收窄创建者权限；成员移除、KB 撤权后即使 Key 有效也立即失效。
- 页面默认单库、只读 + `ask`；多库需要显式确认；不提供全租户 Key。
- 不返回对象存储键、内部连接串、未授权来源；引用必须来自本次授权证据集。
- 资源读取每次重新授权，不能依赖列表时的可见性。
- 审计：Key 创建/撤销已有；FR-9 增加工具级调用审计；导出与保留期沿用现有审计策略。
- 泄露处置：Key 可即时吊销；页面不保存明文；建议默认 30 天过期。

## 9. 页面信息架构

接入页调整为三段式：

1. **连接**：知识库多选、Key 名称、有效期、生成按钮、范围提示；
2. **验证与配置**：自检步骤结果、客户端模板 tab、可编辑 API 地址/二进制路径、复制配置；
3. **获取与治理**：Release/镜像获取、版本兼容、工具清单、用量入口（跳转 `/ops` 的连接视图）、吊销入口。

状态处理：无知识库、无权限、Key 已过期、自检失败、模型超时、文档未就绪都要有明确文案与下一步动作。

## 10. 指标与验收

**产品指标**
- 激活：生成 Key 后 24h 内成功调用一次工具链的比例；
- 获客到成功：页面进入到自检通过的中位耗时；
- 留存：周活跃连接数（按 Key 去重）；
- 质量：`ask` 带引用率、无答案正确拒答率、工具调用成功率、P95 延迟；
- 安全：越权负向零泄漏、过期/撤销 Key 100% 拒绝、跨租户审计查询为零；
- 支持：配置类问题占比与平均解决时间。

**发布验收**
- B16/B21 既有验收全部通过（`scripts/b16_acceptance.sh`、B21 页面流程）；
- 多库、自检、模板、二进制、过期预设各有自动化或可复现脚本；
- 前端单测、`tsc -b`、生产构建、`codegen:check` 通过；
- m1–m7 acceptance 与 m3 eval 门槛不回归；
- 文档更新：`docs/mcp.md`、`docs/operations.md`、`README`、发布说明。

## 11. 风险与开放问题

**风险**
- 多库扩大单 Key 的爆炸半径：默认单库，多库需确认；
- `X-MCP-Tool` 可伪造：只作统计，不作授权；
- 发布矩阵带来支持成本：先覆盖 3 OS × 2 架构，其余按需求追加；
- Resources 可能被用于批量导出：限制列表、逐次授权、记录读取审计；
- 远程传输会改变信任边界：单独设计，不夹带进 B22-A/B。

**开放问题（待 owner 决策）**
1. 多库连接的产品默认值：坚持单库，还是提供“项目级多库”模板？
2. 是否把“连接”做成一等模型（独立 ID、名称、用量），还是继续用 API Key 代表连接？
3. 远程 HTTP/SSE 的目标客户端优先级（Dify/n8n/自研 Agent）与时间窗？
4. 是否发布到 npm/PyPI，还是只提供 Release 二进制与 Docker？
5. 工具级审计的保留期与导出要求是否与 B18 证据链审计合并？
